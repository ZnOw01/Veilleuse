# Veilleuse architecture for Omarchy 4

## Product contract

Veilleuse is one native GTK 4 / Libadwaita application for display brightness and night-light control on Omarchy 4.

It must integrate with Omarchy instead of replacing it:

- brightness writes use `omarchy-brightness-display`;
- brightness reads use the native Omarchy display selection plus `brightnessctl`;
- night-light state and writes use the installed `hyprsunset` IPC;
- the Omarchy shell night-light service is refreshed after successful writes;
- Omarchy's Lua keybindings, Quickshell bar, OSD and service lifecycle remain owned by Omarchy;
- Veilleuse never edits Waybar, `bindings.conf`, `bindings.lua`, `hyprland.conf` or `hyprland.lua`;
- Veilleuse never enables or disables `hyprsunset.service`.

## Runtime components

### `src/native_backends.py`

Defines injected, testable command adapters without `shell=True`.

Public contract:

```python
@dataclass(frozen=True)
class BrightnessState:
    available: bool
    percent: int | None
    monitor: str | None = None
    error: str | None = None

@dataclass(frozen=True)
class NightLightState:
    available: bool
    enabled: bool | None
    temperature: int | None
    identity: bool | None
    gamma: int | None
    error: str | None = None

class OmarchyBrightnessBackend:
    def read_state(self) -> BrightnessState: ...
    def step(self, direction: int) -> BrightnessState: ...
    def set_percent(self, target: int) -> BrightnessState: ...

class OmarchyNightLightBackend:
    def read_state(self) -> NightLightState: ...
    def set_temperature(self, kelvin: int) -> NightLightState: ...
    def set_natural(self) -> NightLightState: ...
    def set_gamma(self, percent: int) -> NightLightState: ...
    def reset_gamma(self) -> NightLightState: ...
```

Rules:

- command argument arrays only;
- bounded timeouts;
- state is refreshed from hardware after writes;
- brightness changes generated by the GUI are at most one percentage point per backend operation;
- `set_percent()` converges through bounded one-point calls and is cancellable by the caller;
- successful night-light writes trigger best-effort `omarchy-shell -q nightlight refresh`;
- shell refresh failure does not turn a confirmed hyprsunset write into a false failure;
- natural color uses `hyprctl hyprsunset identity` and readback confirmation;
- the backend never starts another `hyprsunset` process.

### `src/veilleuse.py`

One `Adw.Application` with APP_ID `io.github.ZnOw01.Veilleuse` and one adaptive application window.

Visible layout:

1. compact status header with hardware/backend availability;
2. `Pantalla` section: real brightness percentage, accessible slider and minus/plus buttons;
3. `Luz nocturna` section: enable/natural state, temperature and gamma controls;
4. `Horario` section: day/night time and night temperature, reusing conservative schedule parsing and atomic writes;
5. non-modal toasts for confirmed success and actionable failure.

The UI must not expose implementation terms such as IPC, identity matrices, processes or Waybar.

### CLI

A single `bin/veilleuse` command provides `--status`, `--toggle`, `--natural`, `--temperature`, `--gamma`, `--brightness` and GUI launch behavior. It uses the same backends as the GUI.

## Installation contract

The installer owns only:

- `~/.local/bin/veilleuse`;
- Veilleuse Python runtime modules in `~/.local/lib/veilleuse/`;
- `~/.local/share/applications/io.github.ZnOw01.Veilleuse.desktop`;
- `~/.local/share/icons/hicolor/scalable/apps/io.github.ZnOw01.Veilleuse.svg`;
- app-owned metadata under `~/.config/veilleuse/`.

It may seed `~/.config/hypr/hyprsunset.conf` only when that file does not exist. Existing schedules are never overwritten.

Install is idempotent and transactional. Uninstall restores same-named pre-existing files byte-for-byte and mode-for-mode, preserves modified managed files, and supports `--dry-run`.

## Removed legacy surface

The final product does not ship or install:

- `brightness-control` or `night-light-control` launchers;
- `brightness-step`, `night-light`, `night-light-status` or `night-light-toggle`;
- a Waybar module or stylesheet;
- Hyprland keybindings or window rules;
- service enable/disable actions;
- Omarchy 3 migration logic in the normal install path.

A narrowly scoped one-time cleanup may remove only markers and exact payloads proven to have been created by the previous project on this machine. It must not infer ownership from command names alone.

## Quality gates

- strict TDD for every new behavior;
- all historical tests that remain applicable stay green;
- contract tests use fake commands and an Omarchy 4 fixture;
- install-twice/uninstall restores bytes and modes;
- no network, telemetry, sudo, `shell=True`, `eval` or `exec`;
- `desktop-file-validate`, Python compile checks and shell syntax checks pass;
- a real GTK launch is verified through the installed desktop entry;
- real brightness and night-light operations are tested conservatively and restored to their original state.
